Expand description

A wire request — one JSON object per line, discriminated by op.

Unknown ops fail deserialization; hosts should treat that as a protocol error and surface the driver’s raw error text.

Variants§

§

Manifest

{"op":"manifest"} → DriverManifest. Discovery verb — cheap, must not require product state.

§

Views

{"op":"views"} → Vec<ViewSummary> — view ids/titles/routes without the full trees (lightweight listing).

§

View

{"op":"view","view":"board","params":{…}} → ViewResult — the resolved tree plus query-fed data for one view.

Fields

§view: String

View id from the driver’s manifest (board, item).

§params: Map<String, Value>

Caller-supplied params merged into each query binding.

§

Query

{"op":"query","query":"items","params":{…}} → QueryResult — execute a single named query binding (or raw product op, for thin drivers) and return its data payload.

Fields

§query: String

Query name from the view’s queries bindings, or a raw product op when the driver proxies serve.

§params: Map<String, Value>

Params merged into the binding’s static params.

§

Render

{"op":"render","kind":"graph","node":{…},"data":{…}, "surface":"cli","format":"svg"} → [RenderModel] — the renderer-plugin verb. node is the raw ViewNode JSON (the host passes it untyped so unknown/future fields survive); data is the view’s query-binding map verbatim; surface is "cli", "tui", or "web" (open string — hosts may add surfaces); format is the surface’s format hint ("svg", "ascii", …) when one applies.

Fields

§kind: String

The node’s kind — also the renderer claim key.

§node: Value

The node as raw JSON (a ViewNode object, {"kind":…}).

§data: Map<String, Value>

The view’s bound query data — the same map view results carry, so the plugin can resolve node.query itself.

§surface: String

Target surface — "cli", "tui", "web".

§format: Option<String>

Optional format hint (CLI --format value, etc.).

§

Submit

{"op":"submit","view":"settings","form":"prefs", "values":{"theme":"dark"}} → SubmitResult — the form-submission verb. view is the view id the form node belongs to; form optionally names the form node’s id (its NodeBase::id) when the view has several forms — drivers resolve the node to read its submit_op and field declarations. values maps each submitted field’s key to its JSON value (string/number/bool per field kind). Drivers that don’t implement forms answer ok:false.

Fields

§view: String

View id from the driver’s manifest — same namespace as the view op.

§form: Option<String>

Optional form-node id (NodeBase::id of the form node); absent submits the view’s default form.

§values: Map<String, Value>

Submitted field values keyed by FormField::key. Keys the driver doesn’t know are ignored; missing required fields come back in SubmitResult::errors.
