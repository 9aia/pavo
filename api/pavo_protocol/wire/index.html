Wire ops — the ndjson JSON-RPC convention every sibling serve speaks, applied to pavo drivers.

Transport: one JSON object per line on stdin/stdout (CLI/TUI) or bridged to ws/http by pavo serve (web). Requests are {"op":"…", …}; responses are {"ok":true,"result":…} or {"ok":false,"error":"…"}. This is the same shape as tamias-serve, myco serve, cuora serve, sepia serve.

Ops (v1):

jobs and notifications are the platform-feed ops: drivers whose manifest declares the matching contributes slot (jobs/notifications) answer them with item lists — see crate::platform. Both are optional capabilities: drivers without the feed answer ok:false (or []) per the usual convention, and hosts treat either as “no feed”.

submit is the form-interaction verb: a renderer collects the editable crate::view_node::FormField values of a form node and posts them here. view names the view the form lives in; form optionally names the form node’s id when a view carries several forms (absent = the driver’s default/first form); values maps field key → submitted JSON value. The driver dispatches on the form’s submit_op; the result may carry a message, per-field validation errors, driver data, and an updated view for re-render.

render is the view-kind renderer-plugin verb: a driver whose manifest declares renderers answers it with a canonical crate::render_model::RenderModel for one node on one surface. Drivers that declare no renderers may ignore it (hosts only call it for kinds the manifest claims).

Thin drivers may proxy a product’s existing serve for query payloads; manifest/views/view are always answered by the driver itself.
