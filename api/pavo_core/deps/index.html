Module deps 

Source
Expand description

Driver dependency ordering — topological sort over the pavo_protocol::DriverDeps declarations manifests carry.

A driver’s deps.requires names drivers it cannot function without; deps.optional names drivers it uses when present. Both kinds of edge mean the same thing for ordering: the dep sorts before the dependent. The differences are in validation:

  • requires naming a driver that isn’t discovered is a hard error (DepsError::Missing) — the dependent can’t function, so the host quarantines it (see crate::host::Host).
  • optional naming an absent driver is fine — no edge, no error.
  • Cycles — including a driver requiring itself — are a hard error (DepsError::Cycle).

Ordering is deterministic: among drivers whose deps are all satisfied, the alphabetically smallest kind is emitted next — dep order first, driver name ascending as the tie-break (the same substitution chrome merge makes for discovery order).

Drivers whose manifests aren’t known yet (deps: None — the lazy-manifest case) contribute no edges and sort unconstrained; crate::host::Host validates their requires when the manifest arrives over the wire.
