Host — the composition root renderers talk to.

Lifecycle: Host::discover scans for pavo-capable drivers and keeps their manifests (eager where the manifest verb answered, lazy via the serve wire otherwise). From there:

  • Host::chrome merges every driver’s contributes into one Chrome (see crate::merge for the ordering policy).
  • Host::list_views / Host::list_routes enumerate what the host can show — namespaced <driver>:<view> ids included.
  • Host::resolve_view turns a deep link ("myco:board", or a bare "myco" for the driver’s first view) into a ViewResult by spawning/using that driver’s serve client.
  • Host::query / Host::client are the escape hatches for view-model ops and form submits.

View results are cached in a TtlCache (default 10s, Host::with_view_cache_ttl) keyed by driver:view + canonical params — repeat renders of the same deep link don’t respawn round-trips. serve clients are spawned lazily on first use and live until the Host drops (each DriverClient’s Drop kills its child).

Host is Send + Sync and every method takes &self — share one behind an Arc (e.g. pavo serve’s per-connection threads). Concurrency is serialized per driver: each DriverClient sits behind its own Mutex, so requests to different drivers proceed in parallel while requests to the same driver stay one-in-flight on its single serve process (the ndjson wire is request/response ordered — interleaved writes would misattribute responses).

Errors are typed: PavoError::UnknownDriver / PavoError::UnknownView / PavoError::BadViewRef for bad targets, driver/transport errors propagated from the client.
