Renderer registry — collect renderers declarations from every discovered driver’s manifest into a kind → driver lookup, and find the plugin-rendered nodes inside a resolved view tree.

This is the manifest half of the view-kind renderer contract (the wire half is the render op, see crate::client::DriverClient::render): a driver declares pavo_protocol::RendererDecls; the host routes matching nodes to that driver’s serve process and gets back a pavo_protocol::RenderModel.

§Claim resolution (deterministic)

  • Explicit kinds beat "*". A renderer listing "graph" always wins over a catch-all for the same node.
  • Among competing claims for one kind (or the wildcard pool), lowest RendererDecl::priority wins; ties break by driver kind ascending, then renderer id ascending — the same policy crate::merge applies to chrome contributions (driver-name order substitutes for discovery order for determinism).
  • Built-in kinds are not reserved. A plugin may claim graph (or even table) and override the host’s built-in rendering on the surfaces it declares — that is the migration path. Kinds no plugin claims keep their built-in interpretation, and unknown kinds still degrade to KV.

Surface matching: "cli" requires surfaces.cli; a format argument further narrows to cli.formats (empty = wildcard, claims every format including text). "tui" requires surfaces.tui == true; "web" requires surfaces.web present.
