pavo-driver-kit — driver authoring for pavo view drivers.

A tamias-driver-<type> executable is mostly boilerplate: the same ndjson serve loop, the same manifest/view struct literals, the same ok:true/ok:false plumbing — duplicated across every driver in the suite (myco, cuora, sepia, sturn, mimus, tamias, …). This crate absorbs the boilerplate so a driver’s UI surface is pure declaration: build a manifest::Manifest, answer ops with serve::serve_stdio, and spend the rest of your time on data.

The kit is deliberately small — four modules, no framework:

  • [serve] — the ndjson request/response loop every driver re-implements ({"op":"…"} in, {"ok":…} out, one per line).
  • manifest — fluent builders for [DriverManifest], [ViewSpec], [QueryBinding], and [Contribution] — including the deps and cross-driver (QueryBinding.driver) declarations.
  • node — [ViewNode] constructors plus a node::Base builder for the shared id/title/query/description/props fields.
  • platform — [JobItem] / [NotificationItem] constructors for the jobs/notifications feed ops.

All types are pavo-protocol’s — the kit adds constructors and the loop, never a parallel type hierarchy. Anything the kit doesn’t cover, drivers write against pavo-protocol directly.

§Minimal driver

use pavo_driver_kit as kit;
use pavo_protocol::wire::{Request, Response};

fn main() {
    let manifest = kit::Manifest::new("demo", "Demo")
        .view(kit::view("board", "Board", "/demo/board",
            kit::column(kit::base().title("Board"), vec![
                kit::markdown(kit::base(), "hello"),
            ])))
        .build();
    kit::serve_stdio(|req| match req {
        Request::Manifest => Response::ok_typed(&manifest),
        Request::Views => Response::ok(serde_json::json!([])),
        _ => Response::err("unsupported op"),
    })
    .ok();
}

See examples/drivers/ for full drivers; crates/pavo-driver-config is the first-party Rust driver (it predates the kit and shows the hand-rolled equivalent).

Modules§

manifest
Manifest builders — DriverManifest, ViewSpec, QueryBinding, and Contribution as fluent data, not struct literals.
node
ViewNode constructors — the declarative tree as function calls instead of nested struct literals (or JSON).
platform
Platform feed constructors — JobItem and NotificationItem, the payloads behind the jobs and notifications wire ops.
serve
The ndjson serve loop — one Request per line on stdin, one Response per line on stdout. Nothing else may touch stdout.
