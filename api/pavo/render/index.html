Module render

ViewNode → text / Graphviz-dot / Mermaid renderers.

The CLI’s view verb renders a resolved [pavo_protocol::ViewResult] on a terminal: --format text walks the node tree and prints a human-readable summary, --format dot/--format mermaid emit the view’s graph nodes in those graph description languages.

Everything works on the node’s raw JSON rather than the typed ViewNode enum so the protocol’s forward-compat rule holds end-to-end: a node whose kind this host doesn’t know degrades to [kv_fallback_json] (a generic key/value listing) instead of failing the render. Query-bound data comes from the ViewResult::data map, keyed by the node’s query field.

Format choices (documented, deterministic):

  • text — containers (panel/row/column) print their title then children indented two spaces per level; row does not attempt side-by-side layout (children stack like column).
  • dot — one digraph block per graph node, concatenated with blank lines, so graphs never merge ids across views.
  • mermaid — a single graph TD merging every graph node in the view; vertex ids are rewritten to n0, n1, … in first-seen order so ids from different graphs can’t collide.

Renderer plugins take precedence over every built-in format except json (the raw ViewResult dump — host-owned, never claimed): for text/dot/mermaid the *_plugins variants substitute a claimed node’s RenderModel (keyed by tree path, see [pavo_core::renderers::plugin_nodes]) and keep the built-in interpretation for everything unclaimed — the same per-node fallback rule the TUI and web surfaces apply.
